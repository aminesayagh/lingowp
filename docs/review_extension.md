## 5. Writing to disallowed locations 🔴

> Plugins must never write to WordPress core directories (such as wp-admin, wp-includes), to other plugins' or themes' folders, to their own plugin folder and only under certain exceptions to the site root, to wp-content or to paths outside the WordPress installation.

Their stated reasons: plugin/core folders are replaced on upgrade; many hosts are read-only or use non-default paths; writing outside expected locations breaks multisite.

Their preference order:

1. Database, via the Settings API — especially for privileged data.
2. Media uploader, for media files.
3. The uploads directory resolved at runtime with `wp_upload_dir()` (never hard-coded), in a folder named after the plugin slug, protected from direct access if not public.

Writing into `wp-content` directly is acceptable only when the plugin's nature genuinely requires it (their examples: caching plugins needing drop-ins, backup/migration plugins).

## 8. Unclosed `ob_start()` 🔴

> Using `ob_start()` without explicitly closing the buffer within the same logical flow […] can lead to unpredictable behaviour. While output buffering is a valid technique, you should not leave a buffer 'open'.

Their reasoning: WordPress is a shared environment; if another component opens or closes a buffer that doesn't align with yours, the buffer stack becomes misaligned.

They note that since **WordPress 6.9** the standardised way to modify the entire response is the template enhancement output buffer.

**Example from the plugin:**
