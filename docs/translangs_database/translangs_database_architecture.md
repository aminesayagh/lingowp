# TransLangs — Database Architecture v4 (Final)

Status: **frozen**. Consolidated after full internal design review plus two
external expert reviews (June 2026). Supersedes v3.

Conventions: `wp_tl_` is the placeholder table prefix (replace with
`$wpdb->prefix . 'tl_'`). `{charset_collate}` is the WordPress
charset/collation clause; **utf8mb4 required**. All tables InnoDB. Tables are
created with raw `$wpdb->query()` DDL — **never `dbDelta()`** (it mangles
FOREIGN KEY clauses). Activation verifies prerequisites and every FK, and
aborts with rollback and a specific human-readable `wp_die()` message on
failure (see §10).

---

## 0. Architecture in one paragraph

Two tables. `wp_tl_source` holds every translatable source string of every
type — post fields, post meta, taxonomy terms, gettext, rendered-HTML
fallback — one row per string, identified by a deterministic structured
binary key. `wp_tl_translation` holds one row per (source, language), and a
row exists **only when a translation has actually been produced**: absence
means "not yet translated." The render hot path never joins and never looks
anything up to find its key — WordPress filter hooks provide the identity
(post ID, field, meta key, term, gettext domain), the key is recomputed in
PHP, and translations resolve in single clustered-index dives, batched per
page. The full deletion chain — WordPress row → source strings →
translations — is enforced end to end by real InnoDB foreign keys, making
translation orphans structurally impossible for owned content.

```txt
wp_posts ─────────────┐  ON DELETE CASCADE
wp_term_taxonomy ─────┤
                      ▼
                wp_tl_source ──ON DELETE CASCADE──▶ wp_tl_translation
                (5 types,                           (1 row per source × lang,
                 1 row per source string)            absence = untranslated)
```

Design standard held throughout: **every column, index, and table must name
the query that pays for it.** Anything without a consumer was removed
(decisions log, §12).

## 1. The source_key — frozen byte contract

Fixed-width **32-byte binary**, four segments, big-endian throughout.
**Identity is locational, not textual** (D26): the key encodes *where a
string lives*, never the string itself — so editing the text keeps the same
key and the translation stays attached. The only exception is plain gettext
(type 4 without context), which has no location and must fall back to text
identity.

```txt
source_key = [ type : 1 ][ owner_id : 8 ][ H(ref1|ref2) : 8 ][ tail : 15 ]
```

| Segment | Bytes | Content |
|---|---|---|
| `type` | 1 | `1`=post · `2`=postmeta · `3`=terms · `4`=i18n (gettext) · `5`=html |
| `owner_id` | 8 | `pack('J', post_id)` for types 1–2; `pack('J', term_taxonomy_id)` for type 3; **8 zero bytes** for types 4–5 |
| `H(ref1\|ref2)` | 8 | first 8 bytes of SHA-256 of `ref1 . '|' . (ref2 ?? '')` |
| `tail` | 15 | **types 1,2,3,5: 15 zero bytes** (identity is fully locational — `[type][owner][H(ref1\|ref2)]` already uniquely names the location). **type 4 only: first 15 bytes of the text hash** — plain `__()` has no location, so text is its identity |

What `H(ref1|ref2)` resolves to per type, and why it is a stable location:

| type | owner_id | ref1 | ref2 | the location it names |
|---|---|---|---|---|
| 1 post | post_id | field | — | "post 42's title" |
| 2 postmeta | post_id | meta_key | context path / NULL | "post 42's `_yoast_title`" / "post 42's `slides.0.title`" |
| 3 terms | term_taxonomy_id | field | — | "term 9's name" |
| 4 i18n | 0 | domain | gettext context / NULL | `_x()`: domain+context is the location; plain `__()`: + text tail |
| 5 html | 0 | selector | — | "the node at this DOM selector" |

`current_hash` (a separate mutable column, §2) is the SHA-256 of the
**normalized current text** — used for staleness detection, NOT identity.
Normalization (frozen, applied identically everywhere): line endings →
entity decode → trim → collapse internal whitespace → UTF-8.

### Contract rules

1. Keys are generated by **exactly one PHP function** (the chokepoint). It
   enforces per-type shape and the type-5 selector cap (≤100 chars). No
   inline key construction anywhere.
2. The byte layout is a **versioned contract**: changes require a
   key-rebuild migration, documented here first.
3. Big-endian `owner_id`: binary order = numeric order ⇒ prefix range scans
   (all of one post's strings are one contiguous range) and physical
   locality (one post's translations cluster on adjacent B-tree pages).
4. Locational identity (D26) is what makes edits non-destructive: a title
   edit changes `original_text` and `current_hash` but not `source_key`, so
   the translation row stays attached and is merely flagged for review
   (§4, §5.6).
5. Type-4 text tail truncation: 15 bytes is collision-safe far beyond
   realistic gettext-catalog sizes. The middle segment can collide only
   within one owner/domain — irrelevant scope.
6. `binary(32)` not varchar: byte comparison, no utf8mb4 collation cost.

## 2. Schema — complete DDL

```sql
CREATE TABLE wp_tl_source (
    id               bigint(20) unsigned NOT NULL AUTO_INCREMENT,
    source_key       binary(32)   NOT NULL,
    type             tinyint unsigned NOT NULL,           -- duplicated from key for readable queries
    post_id          bigint(20) unsigned NULL,            -- set for types 1,2 only
    term_taxonomy_id bigint(20) unsigned NULL,            -- set for type 3 only
    ref1             varchar(191) NOT NULL,               -- §1 mapping
    ref2             text         NULL,                   -- §1 mapping
    current_hash     binary(32)   NOT NULL,               -- SHA-256 of current normalized text; MUTABLE, updated in place on edit; staleness detection only, NOT identity
    original_text    longtext     NOT NULL,
    status           tinyint unsigned NOT NULL DEFAULT 0, -- §4
    source_url       text         NULL,                   -- type 5 diagnostic: last URL seen
    created_at       datetime     NOT NULL,
    updated_at       datetime     NOT NULL,               -- doubles as last-seen for types 4-5
    PRIMARY KEY (id),
    UNIQUE KEY uniq_key (source_key),
    KEY idx_post (post_id),
    KEY idx_tt (term_taxonomy_id),
    KEY idx_admin_queue (status, updated_at),
    CONSTRAINT fk_src_post FOREIGN KEY (post_id)
        REFERENCES wp_posts (ID) ON DELETE CASCADE,
    CONSTRAINT fk_src_tt FOREIGN KEY (term_taxonomy_id)
        REFERENCES wp_term_taxonomy (term_taxonomy_id) ON DELETE CASCADE
) ENGINE=InnoDB {charset_collate};

CREATE TABLE wp_tl_translation (
    source_key      binary(32) NOT NULL,
    lang_id         tinyint unsigned NOT NULL,
    translated_text longtext   NOT NULL,
    translated_against_hash binary(32) NOT NULL,          -- source current_hash AT translation time; frozen; compared to source.current_hash at render to detect staleness
    status          tinyint unsigned NOT NULL DEFAULT 1,  -- §4
    provider_id     tinyint unsigned NULL,                -- §3 dictionary
    created_at      datetime   NOT NULL,
    updated_at      datetime   NOT NULL,
    PRIMARY KEY (source_key, lang_id),
    CONSTRAINT fk_tr_source FOREIGN KEY (source_key)
        REFERENCES wp_tl_source (source_key) ON DELETE CASCADE
) ENGINE=InnoDB {charset_collate};
```

### Index inventory — every index has a named consumer

| Table | Index | Named consumer |
|---|---|---|
| source | PRIMARY (id) | sequential insert clustering; admin row identity; cursor for maintenance walks (§8) |
| source | uniq_key (source_key) | discovery idempotence (`INSERT … ON DUPLICATE KEY`); FK target for translations |
| source | idx_post | WP→source cascade entry; admin "all strings of this post" |
| source | idx_tt | WP→source cascade entry; admin "all strings of this term" |
| source | idx_admin_queue (status, updated_at) | translation work queue `WHERE status=0 ORDER BY updated_at DESC` with keyset pagination (§6.3). InnoDB implicitly appends the PK, so `id` is available as the keyset tiebreak for free — do NOT list it explicitly. Cheap to maintain: source is the low-write table (discovery-only) |
| translation | PRIMARY (source_key, lang_id) | **the** index: render dives, FK satisfaction (leftmost prefix), cascade ranges, per-source language matrix, prefix range scans |

The translation table has **one index**. Deliberate: it is the highest-write
table (machine-translation bursts), and the clustered PK serves every hot
and lifecycle query shape. Admin-comfort indexes on it are deferred behind
measured thresholds (§7).

### Per-type column shape (enforced in the key chokepoint)

| type | post_id | term_taxonomy_id | ref1 | ref2 | source_url |
|---|---|---|---|---|---|
| 1 | ✔ | NULL | field | NULL | NULL |
| 2 | ✔ | NULL | meta_key | context/NULL | NULL |
| 3 | NULL | ✔ | field | NULL | NULL |
| 4 | NULL | NULL | domain | reference/NULL | NULL |
| 5 | NULL | NULL | selector | NULL | last URL |

Optional hardening on MySQL ≥ 8.0.16 / MariaDB ≥ 10.4 (second line of
defense; the chokepoint is the guarantee — many WP hosts run older engines):

```sql
ALTER TABLE wp_tl_source ADD CONSTRAINT chk_shape CHECK (
    (type IN (1,2) AND post_id IS NOT NULL AND term_taxonomy_id IS NULL)
 OR (type = 3 AND term_taxonomy_id IS NOT NULL AND post_id IS NULL)
 OR (type IN (4,5) AND post_id IS NULL AND term_taxonomy_id IS NULL)
);
```

Readability over ref1/ref2: a single PHP accessor class exposes typed names
(`->meta_key()`, `->selector()`, `->domain()`); humans never write raw
queries against this table. Optional per-type `CREATE VIEW`s for debugging
only if someone asks.

## 3. Configuration — no languages/providers tables (derived, not assumed)

A reference table is justified by FKs pointing at it, joins reading it, or
SQL-level integrity rules. v4 has none of the three for languages:
`lang_id tinyint` is dictionary-encoded into the translation PK (no FK, no
varchar in any index); language metadata (name, native name, direction, sort
order) is consumed only by PHP display code (no joins); cascade-on-language-
delete is explicitly not required (cleanup is the batched job, §8.1). A
table would cost one query per request to read a handful of never-changing
rows. Therefore:

**Single autoloaded option `translangs_languages`:**

```txt
{ next_lang_id: N,
  languages: [ {lang_id, code, name, native_name, direction, status, sort_order}, … ] }
```

Two obligations carried in code, both routed through **one mutation
function** (same chokepoint philosophy as the key generator):

1. **ID permanence is mechanical.** `next_lang_id` is a monotonic counter
   inside the option: adding a language consumes it; deleting never
   decrements it; lang_ids are **never reused**. A reused id would silently
   resurrect a deleted language's leftover rows as the new language's
   translations.
2. **Concurrent admin writes** are last-write-wins on an option — acceptable
   for a settings screen touched a few times a year, but every mutation goes
   through the single function; no scattered `update_option()` calls.

Other rules:
- Source language = `get_locale()`. Never stored, never a target (UC-L6).
- Soft delete = status flag in config; translations untouched; re-enable is
  instant (UC-L3/L4).
- **Hard delete (UC-L5):** enqueue the batched cleanup job FIRST (§8.1),
  then remove the entry from config. Order matters: config-first would leave
  rows with no surviving record of their language.
- Every write path validates `lang_id` against config (no FK enforces it).

**Providers:** `translangs_providers` option, `provider_id tinyint → name`,
own monotonic counter, same single-mutator rule.

## 4. Status values

**Source `status`:**

```txt
0  discovered   translatable (default)
3  ignored      never translate; render original in every language
```

**Marking a source ignored DELETES all of its translation rows** in the same
operation. Reason: the render path never reads source status (it reads only
the translation table), so absence of children is the only enforceable
signal (D1). Un-ignoring restarts the string from untranslated. UC-R3 is
satisfied by construction: no row ⇒ map miss ⇒ original text.

**Translation `status`:**

```txt
1  machine        machine translated (default on insert)
2  reviewed       human reviewed
4  needs_review   flagged for review
```

Per-language independence (UC-T3/T5) falls out of the row granularity: each
(source, lang) row carries its own status and provider.

### Staleness — edits flag, never destroy (D26/D27)

Because identity is locational, editing a source's text does **not** delete
its translations (the destructive old behavior). Instead:

- On edit (§5.6 / pipeline Path A): `wp_tl_source.original_text` and
  `current_hash` are updated **in place**; `source_key` is unchanged;
  translation rows stay attached.
- Each attached translation carries `translated_against_hash` = the
  source's `current_hash` at the moment it was translated.
- **At render**, after resolving the translation:
  `source.current_hash == translation.translated_against_hash` ?
    - equal → text unchanged since translation → show translation as-is.
    - differ → source edited since translation → **show the translation
      anyway** (site stays fully translated — the chosen default) **and the
      row is treated as `needs_review`**, surfacing in the admin queue with
      a before/after diff. A one-character title edit becomes a one-click
      *approve* (which sets `translated_against_hash = current_hash`,
      status → reviewed), never a re-translation.

Default policy: **stale-but-shown** (fully translated site, possibly
slightly outdated for a pending edit). A site option can switch to
**fall-back-to-original** (no stale text, visible gaps until approval) for
sites that prefer correctness-or-nothing. The render preload already loads
`current_hash` with the source map, so the comparison costs nothing extra.

## 5. Runtime pipeline

### 5.1 Layer order (execution order IS the priority rule)

```txt
1. WP filter hooks      identity resolution (types 1-4)   ← runs first
2. Output buffer        html fallback (type 5)            ← sees hook output
3. Admin marking mode   translator-session wrappers only
```

Structured content always wins over html fallback because hooks fire before
the buffer is parsed — no precedence configuration exists or is needed (D3).

### 5.2 Hook map (types 1–4)

```txt
type 1  posts      the_title · the_content · get_the_excerpt
                   (+ the_posts for builders that bypass rendering filters)
type 2  postmeta   get_post_metadata
type 3  terms      get_term · get_terms · get_the_terms · get_term_metadata
type 4  gettext    gettext · gettext_with_context · ngettext ·
                   ngettext_with_context  (prefer gettext_{domain} where hot)
```

Every hook handler resolves by **location**, not by text (D26). The identity
comes from hook context (post ID, field, meta key, term_taxonomy_id, domain);
the handler computes `source_key` from that location via the chokepoint —
the live text is NOT hashed into the lookup key. Steps: identify location →
`source_key` → read translation from the preloaded map →
`$map[$key] ?? $original`. The page's source rows (with `current_hash`) are
preloaded alongside translations so staleness (§4) is decided in memory.

(Type 4 plain gettext is the exception: with no location, its key includes
the text tail, so the handler does hash the text for these — §1.)

Hard rules:
- **Never query per hook call** (gettext fires 100s–1000s× per page).
- **Never call `get_post_meta()` inside `get_post_metadata`** — recursion.
  Use the preloaded map or `$wpdb` directly.
- Hooks return **raw replaced values only** — never HTML-wrapped. Meta and
  gettext values land in attributes, URLs, JSON, placeholders, SEO tags.

A map miss renders the original, which correctly covers all three cases at
once: not yet translated (UC-T2/R2), content edited since translation (stale
hash — self-correcting, UC-I2 interim), and ignored (rows deleted, §4).

### 5.3 Request-local ownership set → html fallback (type 5)

While the hooks run, the plugin accumulates **the set of text hashes for
which any structured hook computed a key this request** — regardless of
whether a translation existed. This set is the definition of "owned."

The output-buffer parser then walks the final DOM:
1. Prune excluded subtrees (§9.2).
2. For each remaining text node: normalize + hash.
3. **If the hash is in the request-local ownership set → skip** (a
   structured layer owns it; either it was already replaced, or it is
   untranslated structured content that must not be double-handled).
4. Otherwise compute the type-5 key `H(selector)`-segment + text hash;
   replace from the per-URL map if present; else it is a discovery candidate
   (§9.1).

Why this mechanism (D20): it is zero-query, works on a **cold site with no
translations yet** (where "is the buffer text still in source language?"
would wrongly classify every structured string as unowned), and is truthful
by construction — ownership is "a hook claimed it," not an inference from
translation state. It replaces both the earlier translated-buffer rule and
the database hash-check fallback; `idx_hash` stays removed.

### 5.4 Admin marking mode

Active only for a translator session (query flag + capability check).
Wrappers are added **only at display-level hooks** — `the_title`,
`the_content`, `term_name`, `term_description`, and allowlisted gettext
strings — as:

```html
<span class="translangs-edited-text"
      data-tl-source="{type}" data-tl-key="{hex source_key}">…</span>
```

(`<div>` for block content like `post_content`.) The span carries the
identity so the editor UI writes back to the exact source row — no
text-matching round trip. Raw-value hooks are never wrapped. Frontend
visitors never see wrappers: zero cost, zero SEO impact outside translator
sessions.

### 5.5 Hook specification — resolution vs discovery, per type

Each type has two hook surfaces: **resolution** (read path — replace text on
every page view) and **discovery** (write path — insert/update source rows).
For types 1–3 these are different hooks: save-time discovery is preferred
(language-independent, gives the UC-I2 diff point, keeps writes off
pageviews). Types 4–5 have no save event; render-time discovery is the only
option there.

#### Type 1 — post fields (`post_title`, `post_content`, `post_excerpt`)

| Surface | Hooks | Identity available |
|---|---|---|
| Resolution | `the_title` ($title, $post_id) · `the_content` (use `get_the_ID()`) · `get_the_excerpt` ($excerpt, $post) · `the_posts` ($posts, $query) for builders bypassing render filters | post_id + field |
| Discovery | `wp_after_insert_post` — fires once after post, meta AND terms are persisted (unlike `save_post`); one handler re-scans types 1+2 together | full post object |

Guards on discovery: skip `wp_is_post_revision()`, autosaves, non-published
statuses, non-allowlisted post types. Handler = UC-I2: compute the key set
for current field values; delete this post's source rows not in the set
(cascade clears translations); insert new ones. Render hooks ALSO lazily
insert unknown keys (deferred batch, below) — this covers content that
predates plugin installation without a bulk-import step.

#### Type 2 — postmeta

| Surface | Hooks | Identity available |
|---|---|---|
| Resolution | `get_post_metadata` ($value, $object_id, $meta_key, $single) — recursion rule applies (§5.2) | post_id + meta_key (+ context from value parsing) |
| Discovery | `wp_after_insert_post` re-scan (primary) · `added_post_meta` / `updated_post_meta` ($meta_id, $object_id, $meta_key, $meta_value) for meta written outside post saves | same |

**Meta keys are ALLOWLISTED, never denylisted**: `wp_postmeta` is dominated
by `_edit_lock`, ACF field references, plugin state. Default = translate
nothing; admin or per-plugin integration profiles opt keys in. Context
(ref2) extraction parses serialized/JSON values into paths at discovery.

#### Type 3 — taxonomy terms (`name`, `description`)

| Surface | Hooks | Identity available |
|---|---|---|
| Resolution | `get_term` ($term, $taxonomy) · `get_terms` · `get_the_terms` | term_taxonomy_id + field |
| Discovery | `created_term` ($term_id, $tt_id, $taxonomy, $args) · `edited_term` (same args) — both pass `$tt_id` directly | same |

Guard: translatable-taxonomy allowlist. Term META (`get_term_metadata`) is
keyed by `term_id`, NOT `term_taxonomy_id`: if brought into scope (opt-in,
v1.1), the handler must resolve term_id → tt_id via `get_term()` before
computing the key, with ref1 = meta_key mirroring type 2. Core
name/description ships in v1.

#### Type 4 — gettext (resolution = discovery; no save event exists)

| Hooks | Mapping |
|---|---|
| `gettext` ($translation, $text, $domain) | ref1 = domain |
| `gettext_with_context` ($translation, $text, $context, $domain) | ref1 = domain, **ref2 = gettext context** (`_x()`) |
| `ngettext` / `ngettext_with_context` ($translation, $single, $plural, $number, $domain) | singular and plural = TWO source strings, each translated independently |
| `gettext_{$domain}` variants | prefer for hot domains (e.g. woocommerce) |

Discovery uses the ON-DUPLICATE last-seen variant with daily throttle
(§8.2). Plural note: no CLDR plural-form logic is stored; each form is an
independent string replaced by hash.

#### Type 5 — html fallback (not a filter)

`template_redirect` (frontend only, late priority) starts the output buffer;
the callback at request end runs: exclusion pruning (§9.2) →
request-local ownership check (§5.3) → content filters (§9.3) →
resolution from the per-URL map → surviving unowned nodes become discovery
candidates keyed by selector + text hash.

#### Cross-cutting rule: deferred discovery writes (D24)

Render-time discovery (types 4–5 always; 1–3 lazy backfill) NEVER writes
inline inside a hook callback — a GET pageview must not block on INSERTs.
Candidates accumulate in memory during the request and flush as ONE batched
insert on the `shutdown` hook, after the response is sent where supported
(`fastcgi_finish_request()`), with Action Scheduler enqueue as fallback.
Combined with the per-request circuit breaker (§9.3), discovery is invisible
to visitors. All render-time discovery is skipped for `is_admin()`, REST,
AJAX, and cron contexts — only genuine frontend renders feed it. Save-time
discovery (types 1–3) writes synchronously in its admin-side save request,
where latency is acceptable and immediacy is expected.

## 6. Query shapes

### 6.1 Render (hot path — no joins, ever)

Bounds and keys are computed in PHP; one batched query resolves a page:

```php
$key = TL_Key::make($type, $owner_id, $ref1, $ref2, $text_hash); // the chokepoint
```

```sql
SELECT source_key, translated_text
FROM   wp_tl_translation
WHERE  lang_id = :lang
  AND  source_key IN (:k1, :k2, …, :kn);
-- each key: one clustered-index dive; row data is on the leaf page
```

**Chunk IN-lists at ~150–200 keys** (several small queries, not one giant
one). Rationale: bounded packet/statement size and predictable execution —
*not* optimizer fear; equality lookups on the clustered PK have no bad plan
to fall into even past `eq_range_index_dive_limit` (D17).

### 6.2 Prefix range scans (the structured key paying rent)

```sql
-- everything translated for post 42 in French — no join, no LIKE:
-- PHP: lo = chr(1).pack('J',42).str_repeat("\0",23)
--      hi = chr(1).pack('J',43).str_repeat("\0",23)
SELECT source_key, translated_text, status
FROM   wp_tl_translation
WHERE  source_key >= :lo AND source_key < :hi
  AND  lang_id = :lang;

-- whole gettext set for one language (once per request, cached; §7):
--      lo/hi = type-4 segment bounds
SELECT source_key, translated_text
FROM   wp_tl_translation
WHERE  source_key >= :lo AND source_key < :hi
  AND  lang_id = :lang;
-- note: scans the type-4 range across ALL languages and filters —
-- the accepted D11 residual (small set, cached, once per request)

-- all languages of one source string (UC-A4) — contiguous PK prefix:
SELECT lang_id, translated_text, status
FROM   wp_tl_translation
WHERE  source_key = :key;
```

### 6.3 Admin (cold path — where the joins live)

```sql
-- translation work queue (UC-A1/A2), KEYSET pagination — never OFFSET:
SELECT s.id, s.type, s.ref1, s.original_text, t.status
FROM   wp_tl_source s
LEFT JOIN wp_tl_translation t
       ON t.source_key = s.source_key AND t.lang_id = :lang
WHERE  s.status = 0
  AND ( s.updated_at < :last_seen_at
        OR (s.updated_at = :last_seen_at AND s.id < :last_id) )
ORDER BY s.updated_at DESC, s.id DESC
LIMIT 50;
-- uses idx_admin_queue (status, updated_at) + implicit PK suffix for the
-- tiebreak; t.status IS NULL ⇒ not yet translated

-- everything belonging to a post (entry by ID, uses idx_post):
SELECT s.*, t.lang_id, t.translated_text, t.status
FROM   wp_tl_source s
LEFT JOIN wp_tl_translation t ON t.source_key = s.source_key
WHERE  s.post_id = :post_id;

-- text search (UC-A3): WHERE s.original_text LIKE :q — paginated admin
-- screen; add FULLTEXT only if a real site proves it slow.
```

Filtering the queue by *translation* state (e.g. "all needs_review in
French") runs against the translation PK with a lang filter; below the §7
thresholds this is a bounded scan an admin screen tolerates.

## 7. Caching & memory strategy

Per-page cost is **O(page content), not O(catalog size)**, for everything
except gettext — which is small by nature.

| Set | Scope | Mechanism |
|---|---|---|
| types 1–3 | per page | `the_posts` fires per WP_Query (main loop, menus, widgets, related posts) — each triggers one small exact-key batch for that loop's posts/terms/meta. Lazy single lookups for stragglers. **Negative caching mandatory**: store misses as misses, or an untranslated site re-queries every hook call |
| type 4 | per language | **Tier 1 (default, ≤ ~8k strings):** whole-set preload, once per request, object-cached — same cost model as WP loading .mo files (usually < 100 KB). **Tier 2 (auto fallback above threshold):** no preload; lazy batched lookups + negative caching (same machinery as types 1–3). **Tier 3 (backlog, on measured need):** compile the language pack to a generated PHP file returning a static array; OPcache holds it in shared memory across workers; regenerate on translation writes — the same mechanism as WP 6.5 `l10n.php` |
| type 5 | per URL | map keyed `tl:html:{lang}:{url_hash}` |

Object cache keys: `tl:{lang}:{scope}`; invalidate scope on translation
write. Without a persistent object cache, the queries above run per request
— all are indexed and small; this remains cheaper than the .mo parsing WP
already does.

### Deferred indexes — explicit triggers (D21)

Two indexes are consciously **not** in the v4 schema. Both are pure
admin-comfort on the highest-write table, and InnoDB `ADD INDEX` is online,
in-place DDL — retrofitting on a grown site is safe and non-blocking. Add
when a trigger fires, not before:

| Index | Add when |
|---|---|
| `wp_tl_translation (lang_id, status, updated_at)` — review-queue ordering | translations > ~500k rows, **or** the review-queue screen measurably lags |
| `wp_tl_translation (lang_id, source_key)` — language-first range scans | languages > 5, **or** translations > ~500k, **or** gettext preload / language-delete jobs measurably slow |

The plugin self-detects: a weekly job records `COUNT(*)` and language count;
past a threshold, the admin sees a one-click **"Enable large-site indexes"**
maintenance action (runs the `ALTER TABLE` via Action Scheduler). This is
the answer to "one index is too pure": not preemptive weight, a mechanism.

## 8. Lifecycle & maintenance jobs

All bulk jobs follow one pattern: **keyset-cursor batches via Action
Scheduler** — never one giant transaction (long locks, huge undo log,
replication lag, shared-host query kills), never OFFSET.

### 8.1 Language hard-delete (UC-L5 / UC-I5)

```sql
DELETE FROM wp_tl_translation
WHERE  source_key > :last_key
  AND  lang_id = :lang
ORDER BY source_key
LIMIT 5000;          -- repeat, carrying :last_key forward, until 0 rows
```

One ordered walk over the translation PK per job run. Enqueued BEFORE the
language leaves config (§3).

### 8.2 Type 4–5 age-out (required, not optional — D19)

gettext and html sources have no WordPress parent: nothing cascades them.
Without active cleanup they accumulate for years across theme switches and
plugin churn.

- **Last-seen tracking (required):** discovery for types 4–5 uses
  `INSERT … ON DUPLICATE KEY UPDATE updated_at = NOW()`, throttled to once
  per day per key. `updated_at` on these types means "last seen."
- **Age-out job (weekly):** cursor walk on the source PK — no new index;
  a weekly background job can afford one sequential pass (D22):

```sql
SELECT id, source_key FROM wp_tl_source
WHERE  id > :last_id AND type = 5
  AND  updated_at < (NOW() - INTERVAL 90 DAY)
ORDER BY id LIMIT 5000;
-- delete by collected ids; FK cascades the translations; repeat
```

- **Domain cleanup (UC-I3, on plugin removal / theme switch):** same cursor
  pattern with `type = 4 AND ref1 = :domain`. Rare, human-triggered,
  latency-tolerant ⇒ no `(type, ref1)` index unless an interactive admin
  filter by domain is built later (named-query rule).

### 8.3 Content edit (UC-I2)

On save: re-discover the object's strings; delete source rows whose keys no
longer exist (cascade clears their translations); insert new ones. Between
edit and re-discovery, stale hashes simply miss the map and render the
original — the system is never wrong, at worst untranslated.

### 8.4 Engine-enforced chain (UC-I1 / UC-I4)

`DELETE FROM wp_posts WHERE ID = 42` → InnoDB cascades every
`wp_tl_source` row with `post_id = 42` (types 1 AND 2 ride the same FK) →
InnoDB cascades their `wp_tl_translation` rows. Atomic, zero app code. The
second hop is a contiguous PK range wipe thanks to key ordering.

### 8.5 Migration caveat (support documentation)

Backup/migration plugins (Duplicator, search-replace tools) may recreate
tables in arbitrary order and fail on FK dependencies. Documented; the §10
diagnostic screen detects the resulting state.

## 9. Discovery

### 9.1 Mechanisms per type

- **Types 1–4:** discovery rides the same render hooks — first sight of an
  unknown key inserts the source row. Idempotent via `uniq_key`
  (UC-S4). Types 4–5 use the ON-DUPLICATE last-seen variant (§8.2).
- **Type 5:** output-buffer parse, *after* exclusion pruning and the
  request-local ownership check (§5.3). A text node whose hash no structured
  hook claimed this request, surviving all filters below, becomes a type-5
  source row keyed by selector + text hash.
- Known accepted miss (documented): text identical to a structured string
  but hardcoded elsewhere in the template is skipped by the ownership check
  and renders original. Rare; acceptable for the fallback layer.

### 9.2 Location exclusion (subtree pruning)

Skip the node and its entire subtree when any ancestor carries
`data-tl-skip`, `translate="no"`, or `class="notranslate"` (the de-facto
standards — themes already use them). Never descend into:

```txt
script · style · noscript · template · code · pre · kbd · samp · var ·
textarea · iframe · input values
```

WordPress filters automatically add the skip marker to user-generated and
personal content — `comment_text`, `comment_author`, reviews, forum posts,
logged-in user echoes ("Welcome back, X", account pages, order history) —
and to transactional zones: cart, checkout, order confirmation,
search-result echoes, pagination/date/count fragments, admin bar, login
forms. The same marker serves render-skip and discovery-skip: one pipeline.

### 9.3 Content filters (before any type-5 insert)

- no alphabetic characters → skip (prices, separators, IDs)
- date / time / currency / URL / email / phone patterns for the site locale → skip
- below minimum letter ratio → skip
- **hard cap on new type-5 rows per request** — circuit breaker so a
  pathological dynamic page can never mint rows unbounded

These two layers (location + content) are what keep the type-5 set small
and convergent: it ends up holding genuinely hardcoded sentences only.

## 10. Activation, diagnostics, compatibility

**Activation sequence:**
1. Check `wp_posts` and `wp_term_taxonomy` engines. If MyISAM →
   `wp_die("Your {table} table uses MyISAM; convert it to InnoDB to use
   this plugin.")` — specific and human-readable, never a white screen or a
   raw SQL error (MyISAM core tables still exist in the wild).
2. Create both tables with raw DDL inside a guarded sequence.
3. Verify each of the three FKs exists (`information_schema`); on any
   failure, drop created tables (rollback) and `wp_die()` with the specific
   missing constraint.

**Site Health diagnostic panel** (saves support hours; D23):

```txt
TransLangs DB integrity
  wp_posts engine ............ InnoDB ✔ / MyISAM ✘
  wp_term_taxonomy engine .... InnoDB ✔ / MyISAM ✘
  fk_src_post ................ exists ✔ / missing ✘
  fk_src_tt .................. exists ✔ / missing ✘
  fk_tr_source ............... exists ✔ / missing ✘
  deferred indexes ........... not needed / suggested (row count: N)
  orphan sweep (types 4-5) ... last run: date · removed: N
```

**MySQL 8.4 note:** FKs referencing a UNIQUE key (our `source_key`) remain
fully supported; the deprecations target non-unique/prefix references. The
design is aligned with modern MySQL direction.

## 12. Decisions log

| # | Decision | Reason |
|---|---|---|
| D1 | Ignored deletes translation rows | Render never reads source status; absence is the only enforceable signal |
| D2 | Identity resolution via WP filter hooks | Hooks know post/field/term/domain ⇒ no text-match ambiguity; stale hashes self-correct to original |
| D3 | HTML parsing = fallback only; execution order = priority | Hooks fire before the buffer; structured always wins; no precedence config exists |
| D4 | Deterministic source_key, recomputed in PHP, never looked up | Join-free hot path; key is a pure function of hook-provided identity |
| D5 | *(superseded v2→v3)* hash key must not be PK → structured key as natural PK `(source_key, lang_id)` | Key is no longer random: inserts group by owner; FK satisfied by PK prefix; one index total; reads land on the row in one dive |
| D6 | Structured key `[type][owner][H(ref1\|ref2)][text_hash]`, big-endian | Prefix range scans + physical locality inside the one existing index |
| D7 | Languages & providers in autoloaded config, dictionary-encoded tinyint ids; monotonic `next_lang_id` inside the option, never reused; one mutation function | No FK, no join, no SQL integrity rule remains ⇒ a table is ceremony; permanence must be mechanical (reused id = resurrected dead-language rows); option writes are last-write-wins |
| D8 | Review-queue index on translation deferred behind thresholds (was: dropped) | Highest-write table; bounded scans fine to ~500k rows; online DDL makes retrofit safe; self-detect + one-click action (§7) |
| D9 | One source table + one translation table (was 10 tables) | Child rows were identical; type byte encodes the owner; one round trip per page; parents unified so the FK cascade survives (one child FKs one parent; nullable owner columns give per-type WP cascades) |
| D10 | `ref1`/`ref2` replace 7 sparse per-type columns | ref1 NOT NULL enforces shape on every MySQL version; uniform key recipe; readability via PHP accessors |
| D11 | PK order `(source_key, lang_id)`, not `(lang_id, source_key)` | FK needs source_key as index prefix — the alternative forces a duplicate 32-byte secondary index; costs language-locality (accepted: gettext set small + cached; language delete rare + batched; bulk-translate in source_key order to approximate sequential writes) |
| D12 | No per-hook queries; per-WP_Query batches + lazy + **negative caching** | gettext fires 100s–1000s× per page; misses are the common case early in a site's life |
| D13 | No `dbDelta()`; raw DDL + activation verification with rollback | dbDelta mangles FK clauses |
| D14 | Removed: `idx_lang_status`, `idx_hash`, `idx_render`, child `id` columns, `meta_key_hash`, `context_hash`, languages table | No remaining consumer; every survivor maps to a named query (§2 inventory) |
| D15 | selector ≤ 100 chars, enforced in the key chokepoint | Was a silent prefix-index collision; now schema-independent rule |
| D16 | Precedence (reviewed > latest) retained only as residual tiebreak | Identity resolution removed the general collision case |
| D17 | Chunk render IN-lists at ~150–200 keys | Bounded packet/statement size; NOT optimizer fear — PK eq-lookups have no bad plan past `eq_range_index_dive_limit` |
| D18 | gettext cache tiered: preload ≤ ~8k → lazy batched fallback → OPcache-compiled PHP pack (backlog) | 20k+ short strings ≈ 10–25 MB as a PHP array; tier 3 mirrors WP 6.5 `l10n.php` |
| D19 | Type 4–5 last-seen tracking + age-out job are REQUIRED; activation failures produce specific `wp_die()` | No cascade parent ⇒ orphans accumulate for years; MyISAM core tables still exist in the wild |
| D20 | Request-local ownership set replaces translated-buffer rule + DB hash fallback | Zero queries; correct on cold sites (translated-buffer test fails with zero translations); ownership = "a hook claimed it," truthful by construction; `idx_hash` stays removed |
| D21 | `idx_admin_queue (status, updated_at)` added to source; translation admin indexes deferred with explicit triggers + self-detect | Source is low-write ⇒ cheap; queue filesort over millions of rows on a screen translators live in is a real cost. Translation is high-write ⇒ indexes wait for measured need; InnoDB online ADD INDEX makes deferral safe |
| D22 | Maintenance jobs use PK cursor walks, not dedicated indexes | A weekly background job affords one sequential pass; an index is paid on every write forever |
| D23 | Site Health diagnostic panel (engines, FKs, deferred-index suggestion, sweep status) | FK/engine breakage by hosts and migration plugins is a when, not an if; self-service diagnosis saves support hours |
| D24 | Discovery split: save-time hooks for types 1–3 (`wp_after_insert_post`, `added/updated_post_meta`, `created/edited_term`), render-time only for 4–5; render-time discovery writes are batched and deferred to `shutdown` (post-response where supported), never inline | Save events are language-independent and give the UC-I2 diff point; a GET pageview must never block on INSERTs; gettext/html have no save event |
| D25 | Postmeta keys and taxonomies are ALLOWLISTED for discovery, never denylisted; term meta deferred to v1.1 (requires term_id→tt_id resolution) | wp_postmeta is dominated by non-content keys (_edit_lock, ACF refs, plugin state); default-deny is the only safe posture |
| D26 | Identity is LOCATIONAL, not textual: `source_key = [type][owner][H(ref1\|ref2)]` with a zero tail for types 1,2,3,5; text tail kept ONLY for plain gettext (type 4, no location). `original_hash` removed as an identity column | Text-in-key made every edit a new identity ⇒ a one-char title edit destroyed the translation. Locational identity keeps the translation attached across edits; render resolves by location, which the structured hooks always have |
| D27 | Edits flag, never destroy: `current_hash` (mutable, on source) vs `translated_against_hash` (frozen, on translation); mismatch ⇒ show translation + treat as needs_review with before/after diff. Default = stale-but-shown; option = fall-back-to-original | Turns "edit = re-translate from scratch" into "edit = one-click approve"; matches how WPML/serious tools model translation-needs-update; comparison is free (current_hash preloaded with the source map) |

## 13. Implementation order (risk-first)

1. **`TL_Key` chokepoint** — key generation + shape enforcement +
   normalization. The entire §1 contract lives here. Unit-test exhaustively
   (every type, boundary lengths, UTF-8 edge cases, big-endian packing)
   before anything else exists.
2. DDL + activation + Site Health checks (§10).
3. Hook layer + request-local ownership set + per-WP_Query cache with
   negative caching (§5, §7).
4. Discovery filters + exclusion pruning + type-5 circuit breaker (§9).
5. Admin queue (keyset pagination) + marking mode + editor write-back (§5.4, §6.3).
6. Maintenance jobs: language delete, age-out, domain cleanup (§8).
7. Deferred-index self-detect + one-click action (§7). Tier-3 gettext pack
   stays in the backlog until a measured need.
